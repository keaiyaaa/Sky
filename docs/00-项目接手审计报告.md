## 7. 代码质量分析

### 7.1 架构分层 `[代码可见但未验证]`

- **单模块 79 个 Kotlin 文件混装 4 个来源**（主壳 + aerial + asuka + kami + drone），包结构按子项目划分而非按功能分层；无 domain/data/presentation 分层、无 Repository 统一抽象、无依赖注入（各处直接 `new InspectionRepository(context)`、`DroneManager.getInstance()`）。
- **重复实现并存**：3 个未注册的 Application（aerial.MyApplication / kami.KamiApplication / asuka.InspectionApplication）各自实现一套 DJI init；2 个"DroneManager"（drone 包全功能版 vs aerial 包 KeyManager 瘦封装）；2 个连接管理器（drone.DroneManager vs asuka.DjiConnectionManager 假实现）；2 套 VIP 页；2 套本地数据库。
- **巨型类**：`RoutePlanningActivity.kt` 793 行（地图+交互+DB+任务分发+演示）、`DroneManager.kt` 1112 行（注册/连接/遥测/设置/避障全职责）、`Aerial_photography.kt` 1109 行。

### 7.2 语言与一致性

- 纯 Kotlin（无 Java 混用）`[已验证]`；ViewBinding，未用 Compose。
- 个别文件被工具"单行压缩"（`Aerial_photography.kt`、`FlightIntentData.kt`、`LLMService.kt`），**其中 LLMService.kt:93 的字符串围栏剥离逻辑因此损坏**——这是压缩导致真实回归的实证。
- 代码风格总体一致（official style），命名规范尚可。

### 7.4 错误处理与可维护性

- 大量 `runCatching`/try-catch 兜底（DJI 加固库防御、SDK 缺席降级为字符串提示），防崩溃意识好；但**失败常被静默**：设置同步失败仍提示成功、MsdkFlightDataSource 失败静默回落 Mock。
- DAO 层：kami 游标全部 `.use{}` 无泄漏；asuka 存在 N+1 查询（`DataSource.kt:124-150`）与无事务批量插入（`DataSource.kt:31-42`）。

- 测试覆盖：仅 drone 包纯逻辑有 6 个有效用例；DroneManager（1112 行）、全部 Activity、DAO、导出器**零测试**。

### 8.1 分离与守卫

| 检查项 | 结论 |

| 失联/失控处理 | **缺失**：App 层无信号丢失监听逻辑；`setFailsafeAction` 是 stub（`DroneManager.kt:882-893`）；安全寄托于 WPML 元数据 `exitOnRCLost=executeLostAction, executeRCLostAction=goBack`（`WpmlRouteExporter.kt:66-69`），由固件执行 |

| 控制权限/确认回执 | 部分：语音/LLM 指令有二次确认弹窗（`Aerial_photography.kt:748-946`）；任务起飞前仅 Toast 提示，无强确认；上传/启动有回调但结果只 Toast |
| 错误状态下仍能发指令 | **存在风险**：图传设置"同步"在 stub 恒失败时仍提示成功（`FlightSettingsActivity.kt:140`），造成配置生效假象；kami REAL 模式在 SDK 注册状态检查（恒 false）拦截前不会发出指令——该检查反而"因祸得福"挡住了真机指令，但这是断链而非安全设计 |

### 8.2 安全机制现状总评

当前真实落地的飞行安全能力只有：**避障开关下发（含机型能力预检与降级）、主动避障状态查询、WPML 内的固件级安全参数**。App 自身的返航高度/失控行为/新手模式/低电量返航四条安全设置**全部没有下发到飞机的通道**。安全依赖 DJI 固件默认值 + WPML 模板常量。
